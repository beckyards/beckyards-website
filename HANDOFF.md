Built and verified via the local dev server with a temporary `LOCAL_DEBUG_ADMIN_BYPASS` (added, tested — including simulating real dragstart/dragover/drop DOM events to verify the cross-group move logic, since simple synthetic clicks don't trigger native HTML5 DnD — then fully removed each time, verified 0 matches before finishing). **The user is actively using this for real client data** — as of this writing Group A has 21 real clients and Group B has 24 (Preston K., Jeff P., Jeff G., and many more) entered directly through the local dev server; all test rows used `_verify-`-prefixed names and were deleted immediately after each check, real rows always left untouched.
- **New admin tabs: Route and History.** **Route** (`/admin/route-run`) is a field-use checklist: first visit shows a "Route A" / "Route B" picker; picking one gets-or-creates *today's* run for that group (snapshotting each client's name/price/mowing height from Clients at that moment into `route_run_items`) and shows a big-tap checklist (name, cut height, price, checkbox) with a live "X of Y done" count — revisiting the same day resumes the same run instead of duplicating it. **History** (`/admin/route-history`) lists every past run (date, route, progress), newest first, and clicking one reopens that exact checklist via `?runId=` for review or correction. New Supabase tables `route_runs` (route_group + run_date, unique per pair) and `route_run_items` (per-run snapshot, FK to the run and to the original client), both admin-only (RLS on, no public policies), served by a new `app/api/admin/route-runs/route.js`. Verified end-to-end against the real database — created a real "today" run for Route A (all 21 real Group A clients snapshotted correctly), toggled a checkbox and confirmed it persisted and showed correctly in History and via the `runId` view — then **deleted that test run afterward** so the user's actual first use of Route today starts fresh rather than partially checked off by testing.
- **Route can now be completed and instantly resets.** A "Complete Route A/B" button at the bottom of the live checklist marks that run's `completed_at`, then immediately starts a brand-new run for the same group (fresh snapshot from Clients, all unchecked) — so "Complete" both files the finished run into History and hands you a clean route to start again same day. History now shows a Status column ("Completed" / "In progress"). The "Route A" / "Route B" picker buttons were also lightened (font-weight 500, `--a-dim` color) to match the site's less-bold styling convention used elsewhere.
  - **Found and fixed a real race condition while testing this**: opening the Route tab fires its data-loading effect twice under React's Strict Mode (intentional, to surface exactly this kind of bug) — two near-simultaneous "start today's run" requests could each think no run existed yet and both create one, or both snapshot the client list into the same run twice. Fixed at the database level with two constraints: a partial unique index on `route_runs (route_group, run_date) where completed_at is null` (only one *open* run per group per day) and a unique constraint on `route_run_items (run_id, client_id)` (a client can only be snapshotted once per run); the API now catches both constraints' violations and falls back to the row the other concurrent request created, instead of erroring or duplicating. Verified by deliberately reproducing the double-request race and confirming exactly one run and the correct item count resulted.
  - Tested against the real database using Group B only (the user had already started a real, real Group A run for today while this was being built) so as not to disturb it; all Group B test runs were deleted afterward, leaving Group A exactly as the user had left it (0 of 21 checked) and Group B with zero runs, same as before testing.
- **History merged into the Route tab** — the standalone "History" nav link/page was removed (`route-history/page.js` and `RouteHistoryView.js` deleted); the Route tab's picker screen now shows a "History" list right below the Route A / Route B buttons, filtered to **completed runs only** (in-progress runs are intentionally hidden here). "View →" still opens `/admin/route-run?runId=` for that run, and its back-link now reads "← Back to Route" instead of History.
- **First real-world use confirmed working**: as of this writing the user has a real in-progress Route A run (21 clients, untouched by any testing) and had already completed a real Route B run (24/24 checked) using this feature, which correctly generated a fresh reset Route B run (25 clients, picking up a client added to Clients since) — exactly the intended behavior, observed in actual use rather than just test data.
- **Route now tracks money and who helped.** Each live/viewed run shows a "Who helped on this route?" free-text field (new `route_runs.helper` column, click-to-edit-and-blur-to-save) plus a "Total to make" / "Earned so far" stat pair computed from that run's snapshotted item prices (total = every item's price; earned = only checked items' prices) — both at the top of the page, above the checklist. The inline History list (on the Route picker screen) now also shows an **Earned** and **Helper** column for each completed run, computed server-side in `app/api/admin/route-runs/route.js`'s list endpoint.
- **Resolved: the "ByteString" error on every /api/admin/\* route in production.** Root cause was a single corrupted character (a "•" bullet in place of a letter, at the exact same position every time) inside `SUPABASE_SERVICE_ROLE_KEY` in Vercel's production environment variables — introduced by a copy-paste mangling at some point, not a code bug. It only ever affected the live Vercel deployment; local dev never had the issue since `.env.local` was always correct. Found by adding a temporary route that bypassed supabase-js and made a raw `fetch()` directly to Supabase's REST API (postgrest-js normally strips the real stack trace from network errors, which is why earlier diagnostics only ever showed a bare message) — that raw fetch's real error confirmed `keyHasNonAscii: true`. Fixed by deleting the corrupted variable and re-entering it through a plain-text editor (Notepad) as an intermediary to strip whatever was mangling direct pastes. All temporary diagnostic code (stack-trace-in-response, the raw-fetch debug route) has been removed and redeployed — the codebase is back to clean.
  - **New capability this session: Vercel MCP connector access**, giving direct API access to list/inspect deployments (`list_deployments`, `get_deployment`) for this project without needing the user to screenshot the dashboard. Project ID `prj_dI7g0AdlC3YHxnevSvKIp8vmhX2N`, team `beckyards` (or `team_JSvMehA6jky05TxMYhgxoSYZ`). Note: the Observability/Logs API (`get_runtime_logs`, `get_runtime_errors`) consistently 403s even after reconnecting the integration — only deployment/project-listing endpoints work; logs still require the Vercel dashboard UI.
- **Mobile admin experience overhauled.** Below 900px width, the sidebar becomes a hamburger button (top-left) that slides a full nav drawer in from the left with a tap-to-close backdrop, instead of the old behavior of squishing the sidebar into a wrapping horizontal strip. Below 700px, every `.admin-table` (Aeration List, Clients/Misc, and History) renders as stacked cards — each row becomes a bordered card with a `LABEL: value` line per field instead of a tiny horizontally-scrolling table — via `data-label` attributes on each `<td>` plus a CSS-only transform, so no per-page JS changes were needed beyond adding those attributes. Desktop layout (≥900px) is untouched.
  - **Found and fixed a real CSS Grid bug while building this**: `.admin-shell` (`display:grid; min-height:100vh`) had no explicit `grid-template-rows`, so once the mobile nav and its backdrop became `position:fixed` (removing them from grid flow), the only two remaining in-flow children — the new mobile top bar and `<main>` — stretched to fill the entire 100vh between them (`align-content: normal` defaults to `stretch` for `auto` grid tracks with leftover space), inflating the top bar to over double its real height. Fixed with an explicit `grid-template-rows: auto 1fr;` in the mobile media query.

## How this project's accounts are separated from Oskelo

This was a deliberate, explicit decision by the user (see task log) after the very first version of this site was accidentally set up under the Oskelo GitHub/Supabase accounts. Everything was migrated to fresh, separate accounts:

- **GitHub:** account `beckyards` (created 2026-09-13), not `oskeloco-stack`.
- **Supabase:** its own account, org "BeckYards", not the "oskelo.com" org. To have Claude work on this database, the Supabase connector in Claude's settings must be switched to the BeckYards account (Settings → Connectors → Supabase → reconnect, logging into the BeckYards Supabase account) — switching it away from whatever Oskelo has connected, and vice versa when work shifts back to Oskelo. There is no way to have both connected simultaneously.
- **A leftover, empty, orphaned Supabase project** for BeckYards still technically exists under the *Oskelo* Supabase org (`cidhpivtuloosndxvire`) from before the migration — harmless (nothing points to it anymore) but worth deleting eventually next time the Oskelo Supabase account is connected.
